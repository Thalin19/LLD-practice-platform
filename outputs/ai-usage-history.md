# AI usage record

This is a working record of AI-assisted decisions discussed with the candidate. The candidate required explicit permission for work and retained architectural decisions. The rationales below describe the arguments presented during the discussion; they are not claims about independent research or reasoning the candidate did not report.

1. **Structured text submissions and practice interface.** The assistant compared text, code, diagrams, and combinations. The candidate selected structured text and accepted five sections covering requirements, responsibilities, interactions, edge cases, and trade-offs. The proposed rationale was to capture design reasoning with a manageable implementation scope. The candidate later approved Problems, Practice, and History screens, a light theme with teal accents, instructions/rubric beside the editor, read-only submissions, revisions, and manual retries. The assistant implemented that interface and tested it in a real browser using simulated feedback. The preview clearly identifies simulated assessments and uses separate data without loading Groq credentials.

2. **Assessment labels and hybrid evaluation.** The assistant compared written feedback, scores, and assessment labels. The candidate selected labels, rules plus an LLM, and requiring all five sections. The rationale offered was to separate completeness checks from design judgement and avoid implying numerical precision. The candidate approved the five evaluation criteria.

3. **Domain design and modular monolith.** The assistant proposed a modular monolith and the Problem, Attempt, Submission, Evaluation, and Rubric objects. The candidate approved them and the React/TypeScript, Node.js/Express, and SQLite stack. Separating editable attempts, immutable submissions, and evaluation runs makes revision and retry different operations. The candidate then approved five corresponding SQLite tables, JSON answer/feedback fields, and saving submissions plus pending evaluations together in one transaction. The current implementation covers these domain/storage rules with offline tests, including real transaction rollback and stale-write rejection.

4. **Background evaluation and demo identity.** The candidate accepted saving before background evaluation, preserving failures, retrying against the original submission, and creating new attempts for revisions. After discussing authentication work, the candidate chose a single demo learner. The reasoning offered was to focus the two-day prototype on the practice loop and failure behaviour. With permission, the assistant implemented application services connecting these actions to storage. The candidate then approved twelve HTTP routes after discussing the benefit of adding versioned problem details, rubric details, and a server health check to the nine learner routes. The candidate subsequently authorized connecting the background worker and restart recovery. The assistant implemented sequential processing and marking interrupted runs failed for manual retry, consistent with the approved manual-retry rule. Offline integration tests exercise the API and worker using simulated results. Live feedback quality remains untested.

5. **Zero-cost provider selection and evaluation limits.** The candidate rejected any spending on the assignment. With permission, the assistant researched official free-tier documentation and recommended Groq. The candidate proceeded with Groq's Free Plan and created the key themselves. A permitted minimal connection test with `qwen/qwen3.8-27b` returned OK using 16 reported tokens. The candidate later approved local completeness checks, a combined 6,000-character submission cap, one model request per evaluation, a 1,200-output-token cap, grounded concise feedback, and manual retries only. The assistant implemented the prompt, adapter, and single-run processing with injected simulated responses. The candidate then authorized one live evaluation using a short Parking Lot answer. Groq returned HTTP 429; the application saved a rate/quota failure, with no feedback or reported token usage. No automatic retry or second request was made. Live prompt/schema compatibility, resistance to submission instructions, and design-feedback quality remain unverified; the failed check and its limits are recorded in `outputs/live-evaluation-check.md`.

6. **Approved switch to Gemini.** After the Groq rate/quota failure, the candidate requested Gemini and approved Gemini 3.8 Flash. The candidate created and saved the key privately. The assistant changed the production adapter and credential setting, preserved the same rubric, character/output limits and manual-retry policy, and added 18 offline Gemini tests. All 146 backend tests, both TypeScript checks, and the production build pass. The migration itself used no Gemini requests. The candidate subsequently authorized one live Gemini evaluation. It returned HTTP 400; the application persisted PROVIDER_REJECTED, with no feedback or reported token usage. No retry was made. The exact cause remains undetermined because raw provider error bodies were discarded. The Gemini result is recorded in `outputs/gemini-live-evaluation-check.md`; the historical Groq check remains unchanged. Google's Free Tier project setting and disabled billing are required for the candidate's zero-spending constraint.

7. **Gemini rejection diagnosis and correction.** The candidate authorized one diagnostic request to identify the HTTP 400 cause. Google returned INVALID_ARGUMENT with the explicit message that MINIMAL thinking is unsupported for the selected model. The assistant verified the model-specific thinking table and corrected the request to LOW, the lowest documented supported level, while retaining the existing limits and manual retries. The diagnosis and sanitized evidence are saved in `outputs/gemini-diagnostic-check.md` and `.json`. No further live request was made; the corrected request remains unverified live. The initial generic thinking-setting recommendation was incorrect for Gemini 3.8 Flash.

8. **Corrected live verification.** The candidate authorized one further evaluation with LOW thinking. Google returned HTTP 503 / UNAVAILABLE and explicitly stated that the model was experiencing high demand. The production adapter and processor persisted a safe provider-unavailable failure in an isolated check database. No feedback or token usage was reported, and no retry or fallback was made. The sanitized result is recorded in `outputs/gemini-corrected-live-check.md` and `.json`. This confirms the reported service failure, while live completion and feedback quality remain unverified.

9. **Successful live recovery check.** The candidate requested resolution after the high-demand failure. One controlled request with the existing corrected configuration returned HTTP 200 and STOP. All five assessments and three priorities passed the domain validator, and a completed evaluation was persisted and confirmed after reopening SQLite. Usage was 1,056 input tokens and 770 output tokens, 1,826 total. The assistant reviewed the feedback against the Parking Lot requirements and recorded both relevant suggestions and the limited scope of this one-sample check in `outputs/gemini-recovery-check.md`. No automatic retries or runtime/model changes were made. Broader consistency, quality, and injection-resistance evaluation remain pending.

Before submission, the candidate should review the code, tests, provider behaviour, and these notes, and update this record with any suggestions they reject or revise. This document does not claim the complete prototype has been built or evaluated.
